# 二维码、包裹与入出库 · 扩展草案

2026-10-13 根据新增需求整理。`parcels / parcel_records` 已纳入 SQL 与关系图草案，当时为11表77字段；截至2026-10-17 dev为11表80字段；五个包裹接口已纳入 OpenAPI 与 API 设计页。Android、后端与 Agent 均未实现这条业务链路，静态设计上线不表示业务服务已部署。

## 二维码表示什么

二维码保存一个唯一的包裹单号 `parcel_no`。App 生成二维码，也可扫码解码出同一单号，再向后端查询包裹与入出库记录。不需要二维码表，也不需要在数据库保存二维码图片；可以根据单号随时重新生成。

首版将用户所说的“包裹订单号”统一称为包裹单号。数据库内部仍用 `parcel_id` 关联。单号用文本保存，保留前导零；二维码仅包含该单号，不直接包含入库、出库操作。

有已确认的快递运单号时可将其登记为 `parcel_no`；演示无现成单号时由后端生成系统内唯一编号。如果后续需要同时保存自建编号、快递运单号与电商订单号，再分别增加 `tracking_no / order_no`，不假设一个电商订单只对应一个包裹。任意外部二维码中的网址或文本不能直接当作本系统的有效单号，需按已确认的编码规则解析并查询。

**创建包裹 → 返回单号 → App 生成二维码 → 扫码查询 → 管理员确认入库／出库 → 保存记录。** 生成二维码本身不表示已入库；重复扫描只查询，不写操作记录。

## 最小新增表

| 表 | 字段 | 作用 |
|---|---|---|
| `parcels` | `parcel_id` · TEXT · 主键 | 内部包裹 ID，也是创建请求的稳定编号 |
| | `parcel_no` · TEXT · 唯一、非空 | 二维码内容和业务检索单号 |
| | `created_at` · TIMESTAMPTZ | 后端生成的建档时间 |
| `parcel_records` | `record_id` · TEXT · 主键 | 一次确认操作的稳定 ID，网络重试复用 |
| | `parcel_id` · TEXT · 外键 | 引用 `parcels.parcel_id` |
| | `sequence_no` · BIGINT | 同一包裹内递增；与 `parcel_id` 组合唯一 |
| | `action` · TEXT | `inbound / outbound` |
| | `zone_id` · TEXT · 可空 | 入库必填货架／区域；出库由后端保留最近入库位置 |
| | `operator_id` · TEXT · 外键 | 引用 `users.user_id`，由认证身份填写 |
| | `created_at` · TIMESTAMPTZ | 后端生成的实际登记时间 |

新增建议为 10 个字段。首版不录入物品名称、收件人等额外信息；有明确页面或检索需求时再补。固定货架／区域沿用版本化配置，`zone_id` 暂不是数据库外键。

只建档、尚无流水时返回 `pending`；最后一条是 `inbound` 时返回 `in_stock`，是 `outbound` 时返回 `outbound`。当前状态与在库位置从最后一条记录派生，不再重复存储到包裹表。操作按 `sequence_no` 排序，避免同一时间戳的先后歧义；出库后当前位置为空，历史货架仍可回看。

后端在事务中锁定包裹，验证当前状态、分配序号并追加记录。首次操作必须为入库；在库再次入库、已出库再次出库返回冲突。在出库之后再次入库，可形成新一轮入出库记录。首版暂不支持移库、历史记录编辑或离线补录。

记录只追加。同一 `record_id`、同一确认内容重试返回原记录；同 ID 的不同内容返回冲突。操作人与时间由后端填写，Agent 只能读包裹和记录，入出库写入仍由管理员显式确认。

## API 与分工建议

统一前缀 `/api/v1`；以下接口已加入当前 OpenAPI 草案，参数、响应与模拟样例在工作台 API 页展示，均未实现。

| 接口 | 用途 |
|---|---|
| `POST /api/v1/parcels` | 创建包裹；传稳定 `parcel_id`，可传已有 `parcel_no`，否则后端生成唯一单号。相同 ID 的重试返回已有结果，指定不同单号返回冲突。 |
| `GET /api/v1/parcels?parcel_no=...` | 扫码／输入单号后精确查询，返回内部 ID、登记状态和当前位置；无匹配明确返回未建档。 |
| `GET /api/v1/parcels/{parcel_id}` | 读取包裹基本信息与派生状态。 |
| `GET /api/v1/parcels/{parcel_id}/records` | 按序号分页读取入出库历史。 |
| `POST /api/v1/parcels/{parcel_id}/records` | 管理员确认入库／出库，传 `record_id + action`；入库另传 `zone_id`。 |

Android 负责二维码生成、相机权限与扫码、显示查询结果和确认表单；后端负责单号、表与接口、事务及重复请求处理；Agent 通过只读工具查询包裹历史。视觉算法继续输出区域事件与关键帧，不自动修改入出库记录。

先做包裹建档与查询，再做二维码生成／扫描，再接管理员确认与流水，最后接 Agent 读取。用同一单号验证：生成与扫码一致、前导零保留、重复扫码不写入、重复请求不追加、入库后出库及再次入库的顺序、无效单号提示、服务重启后历史可回读。

## 如何关联监控事件

扫码得到单号只能确认包裹登记信息。可用操作时间、摄像头和货架／区域检索 `events`，供管理员查看候选画面；同时间或同货架不能直接证明画面中的动作属于该包裹。

包裹操作记录使用实际登记时间；视频事件使用偏移，只有录像 UTC 起点已校准时才能按登记时间查询。当前未知起点的录像不能自动关联。

首版不在 `events` 里强加 `parcel_id`。若后续要持久保存管理员确认的“包裹—事件”对应关系，再评审单独的关联表，记录确认人和依据；这也不改变原始视觉事件。
