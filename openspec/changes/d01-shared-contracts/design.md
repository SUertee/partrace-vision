# Design

## Context

动机见 proposal.md。[开发计划](../../../docs/DEVELOPMENT_PLAN.md) 已规定交付顺序；当前共享接口文档仍为草案，PR #12 提供待评审的 API/数据库设计。此 change 的验收对象是契约文档和样例，不是业务程序。

## Goals / Non-Goals

让四方能用同一组场景核对契约，形成有版本、有样例、有确认记录的基线。运行性能、模型效果、SDK 真机和端到端持久化由对应开发工作包实测。

## Decisions

- 采用单一 shared-contracts 能力记录交接语义；字段枚举、路径与 JSON schemas 只链接 docs/api，不建立平行定义。
- 先核对 PR #12 的最终评审版本，记录差异与消费方兼容方式，再确认样例；不把当前草案当作已批准契约。
- 契约须分别表达采集覆盖、索引结果与证据可用性，避免用一个空列表隐去未知原因。具体返回格式在 docs/api 评审确定。
- 人工核查记录独立于原始事件；Agent 只读工具与运行控制分别约定，停止场景覆盖迟到返回。
- 各模块确认结果和剩余依赖写入 Issue #1。tasks 完成意味着本 change 的契约交付完成；D01 仍须按开发计划核对固定素材、范围与三个查询，不因归档自动关闭。

## Risks / Trade-offs

- PR #12 评审期间字段可能变化：基于最终版本关联场景；同步同一 PR 的契约和样例。
- 仅模拟样例通过：明确来源，保留 D04-D10 的真实验收要求。
- 旧样例消费方落后：记录版本、受影响模块与迁移方式，禁止静默更改 ID 或时间解释。

## Migration Plan

核对 PR #12 与最新 dev，完成范围和样例交叉检查，修正契约，四方确认后归档。发生分歧时保持活跃提案并更新文档，不宣布冻结；后续行为变化通过新 change 及接口兼容说明处理。
